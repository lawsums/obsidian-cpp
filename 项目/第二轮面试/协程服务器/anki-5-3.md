DECK: 协程服务器面试题

{Q}简单介绍下你的项目？{A}我基于 C++20 协程和 co_async 异步库，从零自研实现了 WebSocket 协议，做了一个多人在线聊天室服务器。整体流程：HTTP 服务监听端口，根据请求头区分普通网页访问和 WebSocket 升级请求；完成标准 WebSocket 握手后建立全双工长连接；服务端用协程处理每个客户端，通过协程条件变量做消息广播，when_any 管控多协程生命周期，支持心跳保活、延迟统计、连接自动回收，单线程高并发支撑大量长连接。{E}
{Q}为什么要用 C++20 协程做网络服务，不用线程/epoll？{A}1. 协程是用户态轻量级，开销比线程小得多，单机可支撑上万长连接；2. 协程是同步写法、异步性能，代码可读性比原生 epoll 回调好太多；3. IO 等待时协程会挂起，不占用线程、不空转，CPU 利用率高；4. 避免了线程的锁竞争、死锁、上下文切换开销。{E}
{Q}你怎么判断 HTTP 请求要不要升级为 WebSocket？{A}读取 HTTP 请求头，判断 Upgrade 字段是否为 websocket；如果是，就走 101 协议升级响应，完成 WebSocket 握手；如果不是，就直接返回前端聊天室 HTML 页面。对应代码就是用 io.request.headers.get 获取头部字段判断。{E}
{Q}WebSocket 握手流程你具体做了什么？{A}1. 客户端携带 Sec-WebSocket-Key 随机串；2. 服务端拼接固定魔数字符串，做 SHA1 哈希；3. 把哈希结果做 Base64 编码，放到 Sec-WebSocket-Accept 响应头；4. 返回 101 Switching Protocols 状态码，完成协议升级。{E}
{Q}你项目里 WebSocket 协议帧是怎么设计的？{A}自己定义了 WebSocketPacket 结构体，包含opcode：区分文本、二进制、Ping、Pong、关闭帧；payload 载荷内容；手动解析协议头：FIN 结束标记、Opcode、掩码位、载荷长度，还要处理 7E/7F 变长长度，做大小端字节序转换，客户端发来的数据还要异或掩码解码。{E}
{Q}为什么要做大小端转换？什么时候需要？{A}网络协议一律是大端字节序，本机是小端；当 WebSocket 载荷长度超过 125，要用 16 位/64 位存储，必须把本机字节序转成网络大端，接收时再转回本机序，否则解析长度会错乱。{E}
{Q}你代码里到处co_await co_await双重等待，为什么？{A}框架里异步接口返回的是Task<Expected<T>>：第一层 co_await：把 Task 交给协程调度器，生成可等待对象；第二层 co_await：真正挂起协程，等待 IO 完成并接收 Expected 错误结果；这是 co_async 框架统一的异步调用+错误处理规范。{E}
{Q}什么是 Task？为什么很多普通函数也要返回 Task？{A}Task 是协程句柄，封装了协程的状态和返回值；有些函数本身是同步逻辑，没有阻塞IO，但也要返回 Task，是为了统一接口风格，全部可以用 co_await 调用，不用区分同步异步写法，框架更规整。{E}
{Q}为什么接受新连接后要用 co_spawn 抛出去？{A}主循环只负责 accept 接收新连接，不能阻塞；如果直接在主循环处理客户端，长连接会卡死主循环，无法接收新用户；co_spawn 把每个客户端处理逻辑提交到协程调度队列，主循环立刻回去继续 accept，实现高并发接入。{E}
{Q}你聊天室怎么实现多人消息广播？{A}用一个全局 Room 结构体，保存消息列表 + 协程条件变量；用户发消息就存入消息列表，调用 notify_all 唤醒所有在线客户端的协程；每个客户端的 roomPoller 协程被唤醒后，主动拉取新消息推送给前端；全程无锁设计，靠协程条件变量等待，不轮询、不浪费CPU。{E}
{Q}roomPoller 协程的作用是什么？{A}每个客户端都有一个独立 roomPoller 协程：一直等待房间消息更新，一旦有新消息，就从上次位置开始遍历未推送消息，通过 WebSocket 主动下发给当前客户端，实现服务端主动推送、群聊广播。{E}
{Q}为什么要用 when_any_common 组合两个协程？{A}每个客户端同时跑两个协程：1. ws->start()：循环接收客户端消息、处理协议心跳；2. roomPoller：循环等待广播消息、主动推送给客户端；when_any 作用：任意一个协程结束，两个都一起退出，保证连接关闭后协程全部回收，不泄漏、不残留僵尸协程。{E}
{Q}你怎么处理 WebSocket 心跳和断线回收？{A}框架封装了 ping/pong 机制，设置超时时间；服务端定时发 ping 帧，客户端回 pong 帧，记录时间差计算网络延迟；如果超时没响应，就判定连接失效，自动关闭 socket、回收协程资源。{E}
{Q}项目里 Expected 是干嘛的？协程为什么不用异常？{A}Expected 是错误包装类型，替代 C++ 异常；协程里抛异常会破坏协程生命周期、难以捕获；用 Expected 可以把网络错误、协议错误、IO 错误用返回值统一处理，协程更稳定，不会随意崩溃。{E}
{Q}你这个协程聊天室相比传统线程池框架优势在哪？{A}1. 协程轻量，单线程支撑上万长连接，并发量远高于线程；2. 同步式代码写法，比 epoll+回调、线程池逻辑更清晰；3. 协程IO等待挂起，无CPU空转，资源占用低；4. 用条件变量实现无锁广播，避免多线程锁竞争；5. 自主实现 WebSocket 协议，懂底层帧格式、握手、编解码原理。{E}
{Q}面试官追问必杀句怎么表述？{A}我这个项目不仅会用协程，还自己手撕了 WebSocket 协议帧解析、封包、掩码、大小端、握手逻辑，不是只调库；同时理解协程调度、Task 模型、事件循环、多协程生命周期管控，网络编程和 C++20 协程落地都有实际项目经验。{E}
