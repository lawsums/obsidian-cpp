DECK: 零声网盘项目面试题

{Q}请介绍一下你这个云盘项目，整体架构是怎样的？{A}本项目是一个基于 Linux 的高并发分布式云盘系统，整体分为三层：客户端层为Qt编写的Windows桌面客户端，通过QNetworkAccessManager发送HTTP请求，处理文件上传、下载与文件列表展示；业务逻辑层以Nginx作为Web服务器和反向代理，接收客户端请求后通过FastCGI协议转发给8个独立C/C++ FastCGI进程，分别处理注册、登录、上传、秒传、文件列表、文件操作、共享列表、共享操作等接口；存储层采用FastDFS分布式文件系统存储二进制文件，MySQL存储结构化业务数据，Redis缓存Token等热数据。核心数据流：客户端→Nginx（HTTP）→FastCGI业务进程→MySQL/Redis/FastDFS→响应返回客户端。{E}

{Q}为什么选择 Nginx + FastCGI 这种架构，而不是直接用一个 HTTP 框架？{A}1.职责解耦：Nginx基于epoll实现高性能HTTP连接管理，支撑数万并发，FastCGI进程专注纯业务逻辑，分工清晰互不干扰；2.C/C++适配友好：FastCGI提供原生C/C++ SDK，可通过FCGI_Accept()循环阻塞接收请求，适配原生C/C++开发，无需适配第三方HTTP框架；3.进程隔离稳定性高：各接口独立FastCGI进程，单个接口崩溃不影响整体服务，spawn-fcgi可统一管理进程生命周期；4.复用Nginx能力：集成fastdfs-nginx-module可直接提供文件HTTP下载服务，无需业务层中转。{E}

{Q}项目的请求处理流程能否详细描述一下？以"上传文件"为例。{A}1.客户端构造multipart/form-data格式HTTP POST请求，请求头携带user、token，请求体包含文件MD5、文件名、大小及二进制文件内容，发送至服务端/upload接口；2.Nginx匹配对应location规则，通过fastcgi_pass将请求转发至10002端口的上传FastCGI进程；3.FastCGI进程阻塞接收请求，先校验Redis中的Token合法性，再解析multipart/form-data报文提取文件元数据与二进制内容，调用FastDFS客户端API写入Storage节点，获取文件唯一URL；4.将文件元数据写入file_info表，在user_file_list建立用户文件关联，更新user_file_count用户文件计数；5.构造JSON响应通过标准输出返回，经FastCGI封装由Nginx回传给客户端。{E}

{Q}项目中各组件的职责边界是什么？如果让你重新设计，你会改变什么？{A}职责边界：Nginx负责连接管理、请求路由、静态文件下载服务；FastCGI进程处理认证鉴权、数据库操作、FastDFS调用等核心业务；FastDFS专注二进制文件持久化与冗余备份；MySQL存储用户、文件元数据、关联关系等结构化数据；Redis缓存Token会话信息，减少数据库查询。重新设计优化点：1.引入消息队列实现上传后异步写库，降低接口响应延迟；2.新增Refresh Token刷新机制，提升会话安全性；3.规范化客户端前置MD5校验，减少无效上传带宽消耗；4.基于Nginx limit_req_zone增加接口限流，适配高并发场景。{E}

{Q}FastDFS 的架构是怎样的？Tracker 和 Storage 分别负责什么？{A}FastDFS由Tracker追踪器和Storage存储节点组成。Tracker负责集群元数据管理、负载均衡，维护所有Storage节点在线状态，不存储实际文件，客户端上传下载前先向Tracker获取可用Storage地址；Storage按Group卷分组部署，同Group内多节点自动数据同步实现冗余备份，不同Group独立存储文件支持横向扩容。上传流程：客户端请求Tracker获取Storage地址→直连Storage上传文件→Storage返回唯一file_id；下载流程：Nginx集成fastdfs模块，解析URL路径直接定位Storage节点返回文件。{E}

{Q}FastDFS 存储的文件 ID 是什么格式？如何通过它找到文件？{A}文件ID格式示例：group1/M00/00/00/wKg0i1769laAUapKAAA7AwV_nec649.png；各字段含义：group1为存储节点所属卷名，M00对应配置中第一个存储路径store_path0，00/00是自动生成的两级子目录，避免单目录文件过多，末尾字符串是基于时间戳、服务器IP、随机数生成的唯一文件名。下载时HTTP请求携带完整file_id路径，Nginx的fastdfs模块自动解析路径，映射到服务器本地真实文件系统路径并返回文件内容。{E}

{Q}FastDFS 如何实现高可用和数据冗余？{A}1.数据冗余：同一Group内部署多个Storage节点，节点间自动异步数据同步，单个节点宕机后同组其他节点可正常提供服务，保证数据不丢失；2.服务高可用：支持部署多台Tracker节点，所有Storage向全部Tracker上报心跳，客户端配置多Tracker地址，单Tracker宕机可自动切换；局限性：Storage数据为异步同步，存在短暂数据不一致窗口，仅适用于最终一致性场景，不适合强一致性业务。{E}

{Q}Nginx 和 FastCGI 之间是如何通信的？底层协议是什么？{A}底层采用FastCGI二进制协议通信，传输介质支持TCP或Unix Domain Socket，本项目使用本地TCP通信。通信流程：1.Nginx接收HTTP请求后，将请求头、请求方法、请求体等信息封装为FastCGI协议数据包；2.通过TCP转发至指定端口的FastCGI进程；3.FastCGI进程调用FCGI_Accept()阻塞接收数据，从标准输入读取请求内容，业务处理后向标准输出写入带HTTP响应头的结果；4.Nginx接收响应数据，封装为标准HTTP响应返回客户端，核心依赖Nginx引入fastcgi.conf配置映射环境变量。{E}

{Q}spawn-fcgi 是什么？它的作用是什么？{A}spawn-fcgi是专用FastCGI进程管理工具，核心作用：1.将普通C/C++可执行程序托管为FastCGI服务，绑定指定IP和端口；2.后台守护进程运行，维持FastCGI进程常驻，持续监听Nginx请求；3.支持批量启动多进程，实现接口隔离与并发扩容。项目中通过脚本用spawn-fcgi启动8个FastCGI进程，分别监听10000-10007端口，对应不同业务接口；相较于传统CGI每次请求fork新进程，FastCGI常驻进程规避频繁创建进程开销，大幅提升并发性能。{E}

{Q}Nginx 的 epoll 模型是如何支撑高并发的？{A}Nginx基于Linux epoll I/O多路复用实现高并发，相较于select/poll，epoll优势显著：1.采用红黑树内核维护监听文件描述符，epoll_ctl仅需一次注册，无需每次全量拷贝fd；2.内核通过回调机制仅返回就绪事件，epoll_wait时间复杂度为O(就绪连接数)，而非O(总连接数)；3.支持边缘触发ET模式，减少无效事件通知。Nginx单进程即可处理数万长连接，本项目依托epoll高效承载Qt客户端HTTP请求，再通过本地TCP转发至FastCGI进程，适配高并发访问场景。{E}

{Q}项目中用户密码是如何存储的？为什么用 MD5？有没有更安全的方案？{A}项目中将用户密码做MD5哈希后，以32位十六进制字符串存入MySQL用户表，客户端登录时本地计算密码MD5上传，服务端直接比对哈希值。选用MD5原因是算法简单、计算速度快、适配开发成本低。MD5存在明显安全缺陷：属于快速哈希算法，易被彩虹表暴力破解，无抗碰撞能力。更安全方案：1.引入随机盐值Salt，存储MD5(密码+盐值)，抵御彩虹表攻击；2.改用bcrypt、scrypt等慢哈希算法，刻意增加计算耗时，提升暴力破解成本；3.全站启用HTTPS，避免哈希值明文网络传输。{E}

{Q}Token 是如何生成、存储、验证的？为什么用 Redis 存 Token？{A}Token生成：用户登录成功后，拼接用户名、时间戳、随机数，经MD5生成32位唯一令牌；存储方式：以Token为键、用户信息为值存入Redis，设置TTL过期时间自动失效；验证流程：客户端每次请求携带Token，服务端查询Redis，命中则鉴权通过，未命中返回401未授权。选用Redis原因：1.性能极高，内存级微秒级读写，适配每个请求都要鉴权的高频场景；2.原生支持Key过期机制，无需额外定时任务清理过期Token；3.隔离会话临时数据与MySQL持久化数据，架构职责更清晰。{E}

{Q}Base64 是什么？项目中在哪里用到了它？{A}Base64是一种二进制转可打印字符的编码方式，将3字节原始数据编码为4字节字符集，包含大小写字母、数字、+、/，编码后体积增大约1/3。项目应用场景：1.文件缩略图等小二进制图片，通过Base64编码转为字符串嵌入JSON数据包传输；2.HTTP请求头携带文件MD5原始二进制字节时，用Base64编码避免不可打印字符解析异常。关键特性：Base64仅为编码格式，不属于加密算法，可直接解码，无任何安全防护能力。{E}

{Q}秒传功能是如何实现的？能详细讲一下吗？{A}秒传基于文件MD5唯一指纹实现文件去重，完整流程：1.客户端上传前本地计算完整文件MD5值；2.调用前置/md5接口，携带用户信息、Token、文件MD5和文件名请求服务端；3.服务端查询file_info表，判断该MD5文件是否已存在；4.若文件已存在，直接给当前用户建立文件关联记录，引用计数加1，无需上传文件内容，秒传成功；若不存在，通知客户端执行完整文件上传；5.文件删除时维护引用计数，计数归零时才删除FastDFS实体文件，实现多用户共享同一份文件，节省存储与带宽资源。{E}

{Q}文件上传的 multipart/form-data 格式是什么样的？服务端如何解析？{A}multipart/form-data是HTTP文件上传标准格式，由随机boundary字符串分隔多段数据，结构包含分隔符、字段描述头、空行、二进制文件内容、结束分隔符。服务端解析流程：1.从Nginx传递的环境变量CONTENT_TYPE中提取boundary分隔符；2.从标准输入读取完整请求体，按boundary切割拆分各个数据段；3.解析每段Content-Disposition头部，提取文件名、MD5、文件大小等自定义字段；4.剥离头部冗余信息，提取纯二进制文件内容，调用FastDFS接口完成上传。{E}

{Q}删除文件时是如何处理引用计数的？为什么这样设计？{A}删除处理流程：1.客户端发起删除请求，服务端校验Token合法性；2.删除user_file_list中用户与目标文件的关联记录；3.查询file_info表对应MD5的引用计数count，count大于1则仅执行计数减1，不删除FastDFS实体文件；count等于1则计数归零，同步删除FastDFS文件与file_info表记录；4.更新user_file_count表，扣减用户文件总数。设计原因：秒传机制下多用户共享同一份文件实体，引用计数可避免单个用户删除文件影响其他用户使用，借鉴C++ shared_ptr引用计数思想，精准管理文件资源生命周期。{E}

{Q}文件下载时的 PV（访问量）是如何统计的？{A}文件PV访问量在下载接口中实时统计：1.客户端请求文件下载时，服务端执行MySQL更新语句，对user_file_list或share_file_list表中的pv字段自增1；2.个人文件列表接口返回数据时携带pv字段，前端展示单文件下载次数；3.共享文件榜单通过对share_file_list表按pv字段降序排序，筛选热门共享文件。统计逻辑与文件下载鉴权、路由逻辑耦合，无需额外中间件，轻量易维护，适配项目业务场景。{E}

{Q}数据库有哪几张表？表之间的关系是什么？{A}数据库共5张核心表：user_info存储用户账号密码邮箱等基础信息；file_info存储文件MD5、FastDFS地址、引用计数等文件元数据；user_file_list作为中间表，维护用户与文件的多对多关联，记录文件名、分享状态、访问量；user_file_count缓存每个用户的文件总数，优化查询性能；share_file_list存储用户分享文件记录，包含访问量与创建时间。表关系：user_info与user_file_list一对多，user_file_list与file_info多对多；user_file_count为用户文件数量缓存表，share_file_list独立存储共享文件数据，与用户表关联。{E}

{Q}为什么要单独设计 user_file_count 表，直接 COUNT(*) 不行吗？{A}不直接使用COUNT(*)查询的原因：1.性能低效，数据量大时COUNT(*)需扫描索引甚至全表，高频查询耗时明显；2.用户文件列表页面每次加载都要查询文件总数，属于高频接口，频繁COUNT(*)会加重MySQL压力。单独设计user_file_count表属于读优化反范式设计，将文件总数作为独立字段存储，查询仅需通过主键索引O(1)直接获取结果；代价是文件上传、删除时需额外维护该表数据一致性，用少量写开销换取大幅读性能提升。{E}

{Q}file_info 表中的 count 字段在并发场景下如何保证原子性？{A}高并发多用户同时秒传同一文件时，先查后改的读写分离写法会出现计数更新丢失。保证原子性方案：直接执行MySQL原生原子更新语句UPDATE file_info SET count=count+1 WHERE md5=?；依托InnoDB行级排他锁，执行更新时锁定目标数据行，其他并发事务需等待锁释放，避免竞态条件。超高并发优化：借助Redis INCR命令实现计数原子递增，利用Redis单线程无并发冲突特性，定时批量同步计数数据到MySQL，进一步分担数据库压力。{E}

{Q}数据库索引应该如何设计？{A}索引设计贴合业务高频查询场景：1.user_info给user_name建唯一索引，适配登录按用户名精准查询；2.file_info给md5建唯一索引，满足秒传MD5快速匹配需求；3.user_file_list给user建普通索引，优化查询个人文件列表，额外建立(user,md5)复合索引，适配用户文件关联校验；4.user_file_count给user建唯一索引，快速查询用户文件总数；5.share_file_list给user建索引、pv建降序索引，适配个人共享文件查询与热门榜单排序。遵循最左前缀原则，不在大文本字段建索引，兼顾查询效率与写入开销。{E}

{Q}Redis 在项目中的作用是什么？如果 Redis 宕机了会怎样？{A}Redis核心作用：专门缓存用户登录Token会话，设置TTL自动过期，替代MySQL高频鉴权查询，提升接口响应速度、降低数据库压力。Redis宕机影响：所有接口Token鉴权全部失效，已登录用户请求均返回401未授权，整体业务服务不可用。优化降级方案：1.双写兜底，Token同步存入MySQL，Redis宕机后降级走数据库鉴权；2.部署Redis哨兵模式，实现主从自动切换，避免单点故障；3.在FastCGI进程内搭建本地LRU缓存，短时兜底缓存热门用户Token，降低宕机影响范围。{E}

{Q}项目中有压测脚本，你是如何做性能测试的？结果如何？{A}采用wrk压测工具对文件列表等核心接口压测，编写Lua脚本指定POST请求方式、JSON请求体与请求头，通过命令指定线程数、并发连接数、压测时长。压测核心接口包含Token鉴权（Redis查询）、MySQL文件列表查询、JSON数据封装三大流程。性能瓶颈主要集中在MySQL查询层面，优化手段：给查询字段建立索引、通过user_file_count规避COUNT(*)统计、热点用户文件列表缓存至Redis，压测后接口并发承载能力与响应延迟均有明显提升。{E}

{Q}如何处理大量并发文件上传？系统的瓶颈在哪里？{A}高并发文件上传核心瓶颈：1.网络带宽，大文件上传场景下服务器出口带宽最先达到上限；2.FastCGI进程模型，单上传进程串行处理请求，并发量受进程数量限制；3.磁盘I/O，FastDFS Storage节点机械硬盘读写速度限制文件写入效率；4.MySQL写入压力，上传后多表同步写入易造成数据库阻塞；5.内存占用，大文件整份载入内存易导致进程内存溢出。优化方案：多部署FastCGI工作进程、SSD替换机械硬盘、引入消息队列异步写库、文件流式分块处理、多Storage节点横向扩容。{E}

{Q}FastCGI 进程中 FCGI_Accept() 是阻塞的吗？多个请求如何处理？{A}FCGI_Accept()是阻塞函数，调用后进程挂起休眠，等待Nginx转发的FastCGI请求，请求到达后函数返回，执行业务逻辑，处理完成后再次循环调用该函数等待下一个请求。单个FastCGI进程串行处理请求，同一时刻仅能处理一个请求。多请求并发处理方式：1.多进程模式，通过spawn-fcgi启动多个工作进程，Nginx轮询分发请求；2.多线程模式，接收请求后交由线程池处理，主线程立即重新监听新请求，提升单进程并发能力。{E}

{Q}项目部署时遇到过 libfcgi.so 找不到的问题，如何解决的？能说说动态库的加载机制吗？{A}报错原因为libfcgi.so安装在/usr/local/lib，不在系统默认动态库搜索路径。两种解决方式：1.建立软链接，将库文件映射到/usr/lib系统目录；2.配置LD_LIBRARY_PATH环境变量临时追加库搜索路径；规范方式是将路径写入ld.so.conf，执行ldconfig更新系统缓存。Linux动态库加载顺序：优先二进制RPATH路径→LD_LIBRARY_PATH环境变量→ld.so.cache缓存→/lib、/usr/lib默认系统目录，动态链接器ld.so按此顺序查找依赖库。{E}

{Q}Nginx 的配置文件中，你配置了哪些关键内容？{A}核心配置分为三部分：1.FastDFS静态资源配置，通过fastdfs-nginx-module模块配置location匹配group路径，直接解析返回Storage文件；2.FastCGI接口路由配置，为登录、注册、上传等8个业务接口分别配置location，转发至对应端口的FastCGI进程，引入fastcgi.conf映射环境变量；3.基础服务配置，监听80端口作为HTTP服务入口，配置连接超时、缓冲区等基础参数，适配高并发连接请求。{E}

{Q}Qt 客户端是如何发送 HTTP 请求的？{A}Qt客户端基于QNetworkAccessManager实现异步HTTP通信：1.通过QNetworkRequest配置请求地址、请求头与数据格式；2.构造QJsonObject封装业务参数，转为JSON字节流作为POST请求体；3.调用post方法发起异步请求，绑定finished信号槽；4.请求完成后读取响应数据，解析JSON结果更新UI界面。文件上传借助QHttpMultiPart构造multipart/form-data格式，文件下载通过readyRead信号流式读取二进制数据，分块写入本地文件，避免内存溢出。{E}

{Q}项目中 JSON 数据是如何序列化和反序列化的？{A}服务端C++采用轻量级cJSON库：序列化通过创建cJSON对象，添加键值对后转为字符串，通过标准输出返回给Nginx；反序列化解析请求体字符串，提取用户、Token等业务参数，使用完毕释放内存避免泄漏。Qt客户端采用框架内置JSON模块：通过QJsonDocument、QJsonObject实现JSON序列化与反序列化，封装请求参数、解析服务端响应数据，无需引入第三方库，适配Qt异步网络请求场景。{E}

{Q}如果让你给这个项目增加一个"断点续传"功能，你会怎么设计？{A}断点续传核心采用分块上传方案：1.客户端将大文件拆分为固定大小Chunk分块，标记每块序号与总块数；2.新增upload_progress进度表，记录用户、文件MD5、已上传分块序号、总块数；3.新增上传状态查询接口，客户端上传前请求接口，获取已完成分块，跳过无需重传；4.客户端逐块上传未完成分片，服务端临时缓存分片数据，同步更新上传进度；5.所有分片上传完成后，服务端合并文件并写入FastDFS，清理临时缓存与进度记录；同时兼容HTTP Range标准范围请求协议，适配通用断点下载场景。{E}
