# 2 笔记

## 2.1 基础入门与第一个 BootLoader
### 2.1.1 单片机为何需要使用 BootLoader
单片机更新
  一种情况是在 Flash 上自更新。但如果单片机 Flash 较小，由于 Flash 上同时存在下载函数和烧录函数，应用代码也在其中，写入时可能会覆盖自身的烧录和下载函数。因此，Flash 较小的单片机不适用于这种更新方式。
  还有一种方式是 Flash 很小但 RAM 很大的情况。此时将 Flash 上的 App 拷贝一份到 RAM 中，平时在 RAM 上运行。更新时，先下载到 RAM，再通过 RAM 覆盖 Flash 上的 App。由于 RAM 中已有一份 App，实时运行时可运行 RAM 中的版本，因此烧录过程不影响应用的正常运行。但是这种方式如果烧写失败的话，Flash 就会报废，这个板子就变成砖头，所以它也有它的缺点。
  最后一个方式呢，就是 Boot Loader, 在 Flash 启动时，我们会优先运行 Boot Order，即在 App 前加一个程序。该程序主要功能是检测是否更新：如果当前不需要更新，则正常执行应用；如果需要更新，则先更新再执行。像刚才烧写失败的情况，说明更新尚未成功，此时会自动重新更新，从而避免 Flash 烧写失败一次后就变砖的问题。
  
### 2.1.2 BootLoader 的功能与必备知识
Boot Loader 的功能其实不止启动应用程序、更新应用程序。像 Linux 里面知名的 U-Boot，它启动之后内置了非常多的函数。
Boot Loader 还内置中断和异常处理的一些函数

### 2.1.3 最简单的 BootLoader 的多种写法
- 第1个BootLoader
APP烧写在Flash上,APP也在Flash上直接运行,BootLoader直接跳到APP位置即可。
 - 第2个BootLoader
APP烧写在Flash上,APP应该在RAM里运行,但是APP会把自己复制到RAM,BootLoader直接跳到APP位置即可。
- 第3个BootLoader
APP烧写在Flash上,APP应该在RAM里运行,BootLoader把APP复制到RAM,再跳到RAM里执行APP。
- 第4个BootLoader
修改异常向量的地址：两种方法
如果硬件支持重新设置异常向量地址，重定向一下就行。如果不支持，需要将老异常向量指向的老函数地址，在老函数中调用新的异常向量。

### 2.1.4 问题
再从跳转过去，这个跳转到 0 x 08040000 的地址。理论上应该直接跳过去，但我们还加了个 1。答案是因为这个：如果 bit 0 是等于 1 的话，我们用的是 Thumb 指令集；如果 bit 0 是等于 0 的话，我们用的是 ARM 指令集。但是呢，就是我们这个 STM 32 F 103 它不支持 ARM 指令集，所以我们必须加 1。
我们应该先烧 bootloader 还是先烧 app 呢？我第一次尝试是先烧 app 再烧 bootloader，但然后就发现这 app 的部分已经被覆盖掉。
第二次先刷 bootloader，再刷 APP，然后在 bootloader 里确认是正确的。
