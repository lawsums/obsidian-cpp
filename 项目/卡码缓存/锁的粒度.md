
### 0.1.1 什么是锁的粒度（Lock Granularity）
锁的粒度描述的是**被锁保护的代码/资源范围的大小**，可以简单理解为：
- **粗粒度锁（大粒度）**：一把锁保护整个共享资源（比如整个缓存），任何线程操作资源的任何部分都要竞争这把锁。
- **细粒度锁（小粒度）**：将共享资源拆分成多个部分，为每个部分单独加锁，线程只需要竞争它要操作的那部分资源的锁，不影响其他部分。

### 0.1.2 这段代码中“锁粒度很大”的具体体现
在你的代码里，所有涉及缓存操作的核心方法（`put`/`get`/`remove`）都使用了同一个 `std::mutex mutex_`，并且是通过 `std::lock_guard` 对**整个方法**加锁：
```cpp
void put(Key key, Value value) override {
    std::lock_guard<std::mutex> lock(mutex_); // 一把锁锁住整个put逻辑
    // ... 所有put逻辑都在锁内
}

bool get(Key key, Value& value) override {
    std::lock_guard<std::mutex> lock(mutex_); // 同一把锁锁住整个get逻辑
    // ... 所有get逻辑都在锁内
}

void remove(Key key) {
    std::lock_guard<std::mutex> lock(mutex_); // 同一把锁锁住整个remove逻辑
}
```
这就导致了以下问题：
- 哪怕两个线程操作**完全不同的 key**（比如线程A操作 key=1，线程B操作 key=2），也必须排队等待这把锁，因为锁保护的是**整个缓存的所有操作**；
- 哪怕是只读的 `get` 操作，也会阻塞其他所有操作（包括其他 `get`），完全无法利用“多读少写”的场景优化；
- 锁的持有时间覆盖了“查找节点→修改节点→调整链表”的全部逻辑，持有时间长，进一步加剧了线程竞争。

简单说：这把锁“管得太宽”，把整个缓存都罩住了，这就是**锁粒度很大**。

### 0.1.3 为什么“不好直接减少锁粒度”
你提到“锁的粒度还不好直接减少”，核心原因是：
- LRU 的核心是**双向链表**，任何节点的访问（`get`）都需要调整链表（把节点移到尾部），这个操作涉及多个节点的指针修改（当前节点的 prev/next、前后节点的指针）；
- 链表是一个“整体化”的结构，调整一个节点会影响链表的多个部分，无法只对单个节点加锁；
- 哪怕用读写锁（`std::shared_mutex`），`get` 操作因为要修改链表（移动节点），也必须用写锁，最终还是和 `put`/`remove` 竞争，无法体现读写锁的优势。

### 0.1.4 “LRU 分片”解决思路（针对大粒度锁的优化）
既然整个 LRU 加锁粒度太大，核心优化思路就是**分片**：
1. 将缓存的 key 分成 N 个独立的分片（比如按 key 的哈希值取模 `hash(key) % N`）；
2. 为每个分片分配一个独立的 LRU 实例 + 独立的锁；
3. 线程操作某个 key 时，先计算 key 属于哪个分片，再只加该分片的锁，操作该分片的 LRU。

这样做的好处：
- 不同分片的 key 操作互不干扰（线程A操作分片1，线程B操作分片2，各自加自己的锁，无需竞争）；
- 锁的粒度从“整个缓存”缩小到“单个分片”，竞争概率大幅降低；
- 每个分片的 LRU 逻辑和你现在的代码完全一致，只是范围变小了，改造成本低。

示例伪代码（分片思路）：
```cpp
template<typename Key, typename Value>
class ShardedLruCache : public KICachePolicy<Key, Value> {
private:
    static const int kShardCount = 16; // 分片数，通常取2的幂
    std::array<std::unique_ptr<KLruCache<Key, Value>>, kShardCount> shards_;
    std::array<std::mutex, kShardCount> shard_mutexes_;

    // 计算key所属的分片
    int getShardIndex(const Key& key) {
        std::hash<Key> hasher;
        return hasher(key) % kShardCount;
    }

public:
    ShardedLruCache(int total_capacity) {
        int per_shard_capacity = total_capacity / kShardCount;
        for (int i = 0; i < kShardCount; ++i) {
            shards_[i] = std::make_unique<KLruCache<Key, Value>>(per_shard_capacity);
        }
    }

    void put(Key key, Value value) override {
        int idx = getShardIndex(key);
        std::lock_guard<std::mutex> lock(shard_mutexes_[idx]); // 只锁对应分片
        shards_[idx]->put(key, value);
    }

    bool get(Key key, Value& value) override {
        int idx = getShardIndex(key);
        std::lock_guard<std::mutex> lock(shard_mutexes_[idx]); // 只锁对应分片
        return shards_[idx]->get(key, value);
    }
};
```

### 0.1.5 总结
1. **锁粒度大**：指用一把锁保护了整个 LRU 缓存的所有操作，哪怕操作不同 key 也会竞争同一把锁，并发效率低；
2. **难以直接缩小粒度**：因为 LRU 依赖双向链表，节点调整涉及多个关联节点，无法仅对单个节点加锁；
3. **LRU 分片优化**：将缓存按 key 哈希分片，每个分片独立加锁，把“全局锁”拆成“分片锁”，大幅降低锁竞争，是这类场景的核心优化方案。
