# Linux Note Organizer（Linux 系统编程 / 驱动笔记整理）

把用户丢过来的 **Linux 系统编程 / 驱动开发学习材料**（课程笔记、视频截图、AI 生成的内容、自己的理解草稿），整理成
`100-学习/120-嵌入式/linux/` 下风格统一的 Obsidian 笔记。

|---|---|

## 1. 命名与位置

- 一律放 `100-学习/120-嵌入式/linux/`，**不建子文件夹**。
- 命名：`<主题>.md`，**中文、不带空格**（沿用现状：`Pthread基本用法.md`、`Socket网络编程.md`）。
  - 讲一组 API 的用法 → `<A>和<B>用法.md`（如 `ioctl和mmap用法.md`）
  - 讲一个机制 → `<机制>机制.md`（如 `Poll机制.md`）
  - 讲一个完整实战 → `<主题>.md`（如 `多线程Socket服务器.md`）
- 若落点其实在别处：
  - 面试问答形式的材料 → 交给 **bago-organizer**（`面试八股文/`）
  - 算法题 → `面试算法题/` ｜ 手写驱动小实验 → `手写驱动/`

**已存在同主题笔记时**：先 `Read` 全文，把新内容**续号并入**（`## 1.7` / `### 1.7.1` 接续最大值），**绝不覆盖**，也不新建重复文件。

## 3. 写法硬性要求

1. **没有 frontmatter**。这个目录的现有笔记一律没有 YAML 头，直接 `# 1 标题` 起头。（和 `170-课程/` 不同，别照搬那套。）
2. **编号风格**：`# 1` → `## 1.1 一、xxx` → `### 1.1.1 xxx` → `#### 1.1.1.1 xxx`。
   **数字编号和中文序号并存**（`## 1.1 一、`），这是本目录的既有风格，必须保持。
3. **每篇开头一个 `>` 引用块**：一句话定位 + **内核侧头文件 / 用户侧头文件** 清单。
4. **callout 只用这几种**：

   | Callout | 用来装什么 |
   | --- | --- |
   | `[!success]` | 开篇「一句话结论」，只有机制类笔记用 |
   | `[!tip]` | 记忆口诀、简化写法、类比 |
   | `[!note]` | 补充细节、版本差异、拔高观察 |
   | `[!warning]` | 常见错误、容易误读的表述 |
   | `[!danger]` | 最致命的坑、会导致卡死/崩溃/数据错的操作 |

5. **代码块**：`c` 语言标注，**注释用中文**，关键处用 **`【】`** 标重点（如 `/* 【关键坑】... */`、`/* 【不休眠】 */`）。
6. **至少一张对照表**（A vs B、或「需求 → 用什么 → 为什么」）+ 一张 **速查表**。
7. **必须有「常见坑清单」**：用 `- [ ]` 任务列表，一条一个坑，写清「错在哪」而不是「要小心」。
8. **`[!danger]` 排查框**：把「典型症状 → 依次排查哪几点」写成一个 callout，这是复习时最值钱的部分。
9. **相关笔记一律用全路径 wikilink**：`[[100-学习/120-嵌入式/linux/xxx.md|显示名]]`，并且**只链真实存在的文件**。
10. **原文信息零丢失**：用户给的内容全部保留，只做结构化 + 补全，不改原意。
11. **补充内容要申报**：自己加的坑清单、示例、对照表，汇报时**逐条列出**。
12. **代码必须能编译级的正确**：不确定的 API 签名、头文件名、内核版本差异，要么查证，要么明写「（版本差异）」。**宁可不写，不要编。**

## 4. 去重：先查再写（**本 skill 最关键的一步**）

`linux/` 下的笔记写的是「**用法 / 实操**」，`面试八股文/` 里写的是「**原理 / 面试答法**」。两者**互为表里、不重复**。

**动手写之前，必须先 Grep 一遍**：

```
Grep pattern="<关键词>" path="100-学习" output_mode="files_with_matches"
```

重点检查这几个文件里是否已有该主题：

| 文件 | 里面通常有什么 |
|---|---|
| `面试八股文/Linux驱动.md` | `file_operations` 各成员、`ioremap`/`mmap`/`remap_pfn_range` 原理对比、内核模块加载 |
| `面试八股文/Linux系统编程.md` | 进程/线程、fork、IPC、文件IO、信号 |
| `面试八股文/编译和调试.md` | GCC / Makefile / GDB |
| `linux/` 同目录其它笔记 | 可能已经有该 API 的一段，需要续号并入而不是另起炉灶 |

**发现已有原理内容时的处理**：
1. `linux/` 笔记里**只写用法**，原理一句话带过；
2. 在相关位置（正文或末尾）**双链互指**，并注明互补关系：
   `- [[.../面试八股文/Linux驱动.md|Linux 驱动（八股文）]] —— 里面有 xxx 的**原理**对比，和本文互为表里`
3. **不改动 `面试八股文/` 里的内容**（那不属于本 skill 的领地）。

## 5. 纠错：材料里的易误读表述要主动指出

用户给的材料来自视频课程 / AI 生成 / 自己的草稿，**几乎一定含有主语不明、层次混淆的表述**。
不要照抄——**先核对，再用表格明确纠正**。

写法：在正文放一张 `❌ 常见误解 / ✅ 实际` 对照表，并把那段放在**第一节**（先纠正理解，再讲用法）。

实例（`Poll机制.md` §1.1）：

| | ❌ 常见误解 | ✅ 实际 |
| --- | --- | --- |
| 驱动 `.poll` 里没数据怎么办 | 在驱动里休眠等数据 | **不休眠**。`poll_wait()` 挂完队列立刻返回 |
| 休眠在哪 | 驱动的 poll 里 | 内核核心层：所有 fd 扫完都没事件，才 `poll_schedule_timeout()` |

> [!tip] 两种纠错措辞
> - 用户的理解**基本对、只是表述含糊** → 「你的图是对的，文字描述差一点」+ 指出是哪一句容易被误读
> - 用户的理解**确实错了** → 直接给 ❌/✅ 对照表，不要绕

## 6. 图片处理

用户的材料常带截图。这些图默认在 `Attachments/`（名称格式 `Pasted image <yyyyMMddHHmmss>.png`）。

1. **找到图**：`Glob pattern="**/Pasted image <前缀>*.png"`，或
   `Get-ChildItem -Recurse -Include *.png | Sort-Object LastWriteTime -Descending`
2. **看图**：直接 `Read` 图片路径（Read 支持 PNG/JPG，会视觉呈现）。**手写笔记图、代码截图一定要看** —— 里面常有用户自己的正确理解，或课程的关键代码。
3. **引用图**：新笔记里用 `![[Pasted image xxxxxxxx.png]]`（Obsidian 会自动解析到 `Attachments/`）。
4. **图里有代码时**：把代码**转写成文字代码块**收进正文（图会丢、代码不会），图可选保留作佐证。

## 7. 执行步骤

1. **定主题与路径**：解析材料主题 → 按第 1 节规则定文件名。已有同主题笔记就先 `Read` 准备续号并入。
2. **读样板对齐风格**：`Read` `Pthread基本用法.md`（标准样板）+ 目标目录中与本次最接近的一篇，确认编号风格、callout 用法、代码注释风格。
3. **看图**（若有）：`Read` 材料里引用的图片，尤其是手写图和代码截图。
4. **去重检索**：按第 4 节 Grep，确认哪些内容已在八股文里、哪些已在同目录笔记里。
5. **核对正确性**：按第 5 节找出材料里的易误读点，准备 ❌/✅ 对照表。**不确定的 API 签名/头文件/版本差异要查证或注明。**
6. **写入**：按第 2 节骨架 `Write` 新文件（或 `Edit` 并入已有文件）。
7. **校验**：
   - 无 frontmatter、`# 1` 起头、编号连续；
   - 开头的 `>` 引用块有头文件清单；
   - 有对照表 + 速查表 + `- [ ]` 坑清单；
   - 所有 `[[wikilink]]` 指向**真实存在**的文件（链前用 Glob 确认）；
   - 代码块标注了 `c`，关键处有 `【】` 标注。
8. **汇报**：见第 8 节。

## 8. 汇报格式

用 wikilink 给出落点，并**分四块**讲清楚：

1. **回答用户的问题**（如果材料里带了疑问）—— 先给结论，再给判定表
2. **文件结构**：一张表格列出各章节装了什么
3. **刻意处理的点**：不重复（链到八股文的哪一篇）、纠错（纠正了哪几处）、版本细节（标了哪些 5.5+/2.6.36 之类的差异）
4. **待确认项**：发现了别处（如八股文）的同类错误 → **列出并询问是否要改，不擅自动手**

## 10. 示例

### 例 A：整理一组 API 用法

用户："能不能在这个文件夹下写一个新文件整理一下 ioctl 和 mmap 的用法？"

- 建 `100-学习/120-嵌入式/linux/ioctl和mmap用法.md`
- 六节：选型表 → ioctl（命令号位域图/四个方向宏/共用头文件/用户态/驱动侧/misc 骨架）→ mmap（零拷贝/用户态/驱动侧 `remap_pfn_range`/三种内存选型表/cache 策略）→ `/dev/fb0` 实战把两者串起来 → 对照表 → 坑清单
- Grep 发现 `面试八股文/Linux驱动.md` 已有 `ioremap`/`remap_pfn_range` 的**原理**对比 → 本篇只写用法，末尾双链互指
- 主动标出 3 个 `[!danger]`：`_IOR`/`_IOW` 方向是「站在用户态」看的、`ioremap` 后的虚拟地址不能 `virt_to_phys`、`remap_pfn_range` 与 `vm_insert_page` 互斥

### 例 B：整理一个机制（带用户的理解草稿 + 截图）

用户："linux驱动里面 poll 的机制是不是这样？把 poll 的基本机制整理到 100-学习/120-嵌入式/linux 里。"（附课程笔记 + 两张截图）

- 建 `100-学习/120-嵌入式/linux/Poll机制.md`
- `Read` 两张图：手写调用链图 + 课程代码截图 → 从代码截图确认「驱动 `.poll` 只有 `poll_wait` + `return` 两行」，与手写图里「挂队列但**未休眠**」吻合
- **先回答**：用户的手写图**对的**，但文字「无数据则进入休眠」主语不明 → 用 ❌/✅ 表在第 1 节纠正
- 正文补图里没有的 3 个关键点：`poll_wait()` 必须无条件调用（附丢失唤醒的 race 推演）、`_qproc` 在 select/poll 与 epoll 下的差异表、唤醒函数要和睡眠状态匹配
