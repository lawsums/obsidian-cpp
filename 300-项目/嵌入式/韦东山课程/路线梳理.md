### 2.1.1 IO 系统
有两套 IO，一套是标准 IO，一套是系统调用 IO
![[Pasted image 20260826104937.png]]
- **APP** 可以直接调用 `open/read/write` 触发系统调用（走右侧直达内核的路径）。
- **APP** 也可以调用 `fopen/fread`，这部分在 C库内部先经过用户空间的 buffer 处理，然后再调用底层的 `open/read/write` 进入内核（走左侧路径）。
所以，你的判断是对的：
- **`open/read/write`** 是用户态的**系统调用 API**。
- **`sys_open/sys_read/sys_write`** 是内核态对应的**具体实现函数**。

**POSIX** 是 **Portable Operating System Interface**（可移植操作系统接口）的缩写, `open/read/write` 也可以说是标准的 POSIX 调用。

### 2.1.3 使用 open 函数创建文件
使用这个 Open 函数创建文件的时候，你要给它的创建行为加上 O_CREAT 和 O_TRUNC，表示这个创建和这个截断。
同时，我们要给它后面的 mode 里面添加相应的权限。如果权限全给的话，就是 0777。0777 表示给读，给这个你自己，还要给组内的所有人**读写执行**的所有权限。
不过实际上，这个给 Group 里面其他人的权限，好像是不能给写权限的。
在 Linux 中，`0777` 是由三个**八进制数字**组成的，它们分别对应三种不同身份的人。
这三位数字从**左到右**，分别代表：
- **第 1 个数字（7）：所有者（User / Owner）**
    - **给谁？**：创建这个文件的**你自己**（或者是文件的主人）。
- **第 2 个数字（7）：所属组（Group）**
    - **给谁？**：这个文件所属的**用户组**。通常是和你同属于一个项目组、同一个部门的一群同事。
- **第 3 个数字（7）：其他人（Others）**
    - **给谁？**：既不是你自己，也不在你这个组里的**所有陌生人**（也就是系统里的其他所有普通用户）。

### 2.1.4 使用 dup 函数
dup 函数的作用是从一个文件描述符复制出一个新的文件描述符。新文件描述符的编号会接着增长，但会继承原文件描述符的读取位置或写入位置。
`dup2(fd1, fd2)` 会让 **fd2** 指向 **fd1** 所指向的同一个文件，fd2 原先指向的文件会被关闭。所以，如果这个 fd 2 本身是标准输入、标准输出或者标准错误的话，就会出现一些有意思的状况，就可以实现类似输出到日志文件里面的效果。

### 2.1.5 Framebuffer 应用编程
首先，对于每个像素点，我们需要计算其偏移地址。偏移地址的计算方式为：Y 坐标乘以 X 轴分辨率，再加上 X 坐标，从而得到该像素点在整个图像中的偏移像素数。然后它偏移的像素数量乘上 bpp 除以 8 就是他的偏移量了。

颜色方面，相似的颜色表示我们一般分为三种方案：

1. RGB 888：对于红、绿、蓝分别分出 8 位，也就是一个字节来表示它们的颜色。每个字节就是每个字节能表示 0~255 的这个颜色范围吗？这个是很经典的 RGB 方案。
2. 第二种是 RGB565，红色用 5 个 bit 来表示，绿色用 6 个 bit 表示，蓝色用 5 个 bit 表示。
3. 还有第三种是 RGB555，就是红绿蓝三种颜色分别用 5 个 bit 来表示。

### 2.1.9 TCP 编程

#### 2.1.9.1 server
一般 TCP 编程分为四步：
1. 创建 Socket
2. 绑定（Bind）：将文件描述符与地址绑定在一起
3. 监听：让文件描述符开始监听，最简便的方式是监听 SO_MAXCONN
4. 接收：通过 accept 函数接收客户端的文件描述符。

韦老师讲的是接收到之后的进一步处理方式。在进一步处理方式中，我们开了一个子进程 fork，在子进程里开一个 while 1 循环，在 while 1 循环里面进行读取。

#### 2.1.9.2 client
客户端部分，我们是用与服务器相同的 IP 通过 connect 函数连接到服务器 socket，连接成功后创建一个 while (1) 循环检测用户输入。如果用户有输入，通过 fgets 获取用户输入，再通过 send 函数发送到服务器。


#### 2.1.9.3 使用 signal 解决僵尸子进程
![[Pasted image 20260901152813.png]]

用法： `signal(信号, 处理方式)`
**每个信号有自己编码好的触发时机**

在这段代码中，`signal(SIGCHLD, SIG_IGN);` 的作用是**避免产生僵尸进程（zombie process）**。

1. **父子进程关系**：
    
    - 主进程（父进程）在 `accept` 到新连接后，调用 `fork()` 创建子进程。
        
    - 子进程负责与客户端通信（`recv` 循环），父进程继续等待新的连接。
        
2. **僵尸进程的产生**：
    
    - 当子进程终止时（例如客户端断开连接，子进程执行 `return -1;` 或 `exit`），内核会保留子进程的退出状态信息，直到父进程调用 `wait()` 或 `waitpid()` 来回收。
        
    - 如果父进程没有回收子进程，这些终止的子进程就会变成僵尸进程（`defunct`），占用系统进程表资源。
        
3. **`signal(SIGCHLD, SIG_IGN)` 的作用**：
    
    - `SIGCHLD` 信号在子进程终止、暂停或继续时发送给父进程。
        
    - 设置 `SIG_IGN`（忽略）后，内核会在子进程终止时自动回收其资源，**不会产生僵尸进程**，父进程也不需要显式调用 `wait()`。

#### 2.2.6.8 驱动模块的 Makefile 模板

这是驱动源码目录里的 Makefile，用于把驱动编译成 `.ko` 模块，并交叉编译配套的测试程序：

```make
# 1. 使用不同的开发板内核时, 一定要修改KERN_DIR
# 2. KERN_DIR中的内核要事先配置、编译, 为了能编译内核, 要先设置下列环境变量:
# 2.1 ARCH,          比如: export ARCH=arm64
# 2.2 CROSS_COMPILE, 比如: export CROSS_COMPILE=aarch64-linux-gnu-
# 2.3 PATH,          比如: export PATH=$PATH:/home/book/100ask_roc-rk3399-pc/ToolChain-6.3.1/gcc-linaro-6.3.1-2017.05-x86_64_aarch64-linux-gnu/bin
# 注意: 不同的开发板不同的编译器上述3个环境变量不一定相同,
#       请参考各开发板的高级用户使用手册

# KERN_DIR = /home/book/100ask_roc-rk3399-pc/linux-4.4
KERN_DIR = /home/book/100ask_imx6ull-sdk/Linux-4.9.88

all:
	make -C $(KERN_DIR) M=`pwd` modules
	$(CROSS_COMPILE)gcc -o hello_drv_test hello_drv_test.c

clean:
	make -C $(KERN_DIR) M=`pwd` modules clean
	rm -rf modules.order
	rm -f hello_drv_test

obj-m	+= hello_drv.o
```

**作用说明：**

- **KERN_DIR**：指向内核源码目录（这里是 IMX6ULL 的 `Linux-4.9.88`，与本节 2.1.6.1 编译的内核一致）。`make -C $(KERN_DIR)` 是"借用内核的 kbuild 构建系统来编译"，所以该内核必须**事先配置、编译过**，否则缺少头文件和编译规则。
- **环境变量**：`ARCH`（目标架构）、`CROSS_COMPILE`（交叉编译器前缀）、`PATH`（编译器所在目录）。不同开发板各不相同，需参考对应手册。IMX6ULL 常用：`export ARCH=arm`、`export CROSS_COMPILE=arm-linux-gnueabihf-`。
- **all 目标**：
  - `make -C $(KERN_DIR) M=$(pwd) modules`：`M=` 指定当前目录为模块源码目录，kbuild 根据下面的 `obj-m` 把 `hello_drv.c` 编成 **`hello_drv.ko`**（可加载模块，不在内核镜像内）；
  - `$(CROSS_COMPILE)gcc -o hello_drv_test hello_drv_test.c`：用交叉编译器把测试程序编成在开发板上运行的 `hello_drv_test`。
- **clean 目标**：清除编译中间产物（`modules.order` 等）和测试程序。
- **obj-m += hello_drv.o**：声明 `hello_drv` 编译为"模块"而非编进内核（对应 `make zImage` 的"内置"）。

> 📌 与本节的关系：2.1.6.7 的 `make modules` 编译的是内核自带的 `<M>` 驱动；**自己写的驱动**则用这个 Makefile 在 `KERN_DIR` 之外单独编译出 `.ko`，之后在开发板上用 `insmod hello_drv.ko` 加载。

#### 2.2.6.9 为什么生成 .ko？为什么 insmod 就能安装驱动？

**为什么不是把驱动编进内核，而是单独生成 .ko？**

- 内核镜像 `zImage` 是**静态**的：内容在编译时就固定了。如果所有驱动都编进去，改一个驱动就要重新编译整个内核并重启，开发和调试太慢。
- Linux 的解决方案是**可加载内核模块**（Loadable Kernel Module）：把驱动独立编译成一个 `.ko`（kernel object）文件，运行时**按需加载**进内核，不用重编内核、不用重启。
- `.o` 和 `.ko` 的区别：
  - `.o` 只是单个源文件的**编译产物**（目标文件），里面调用 `printk`、`register_chrdev` 等内核函数的符号还没解析，地址也没确定，不能直接运行；
  - `.ko` 是在 `.o` 基础上再经过**链接**（`ld -r`，把模块内多个目标文件合成一个）和**可重定位处理**，并附带了模块元数据（`.modinfo` 段：版本号 `vermagic`、许可证、描述、依赖等）。内核拿到它时，才知道怎么把代码装进内存、怎么补全它引用的地址。

**为什么 `insmod hello_drv.ko` 就能把驱动"安装"好？**

`insmod` 不是把文件复制到某个目录，而是把模块**加载进正在运行的内核**，由内核模块加载器完成 4 件事：

1. **加载进内核内存**：通过系统调用 `init_module()` 把 `.ko` 的代码/数据放进内核地址空间（用户程序运行在用户空间，驱动必须运行在内核空间）；
2. **符号解析 + 重定位**：把模块里引用的 `printk`、`register_chrdev` 等**内核导出符号**的地址填上去，让驱动能调用内核函数；
3. **校验版本**：检查模块的 `vermagic`（编译时写死的内核版本 + 配置）是否与当前内核匹配，不匹配会直接拒绝加载——这就是为什么驱动必须用 2.1.6.1 编好的**同一个内核**来编译；
4. **调用入口函数**：执行 `module_init(hello_drv_init)`，也就是 `hello_drv.c` 里的 `hello_drv_init`，它在这里完成真正的注册（比如 `register_chrdev` 注册字符设备、创建设备节点）。到这步驱动才"生效"，应用才能访问它。

对应的卸载：`rmmod hello_drv` 会调用 `module_exit` 的退出函数并释放资源。

> ⚠️ 注意：`insmod` 只是把驱动加载进"**正在运行的内核内存**"，**重启后消失**。想开机自动加载，才需要把 `.ko` 放到开发板文件系统的 `/lib/modules/$(uname -r)/` 下，再 `depmod` + `modprobe hello_drv`。

```bash
Block devices:
  1 ramdisk
  ...
179 mmc
[root@100ask:~]#
```

逐条解释：

1. **`./hello_drv_test`（不带参数）→ 打印 Usage**
   测试程序的 `main()` 会检查参数：`-w <string>` 表示"往设备写一段字符串"，`-r` 表示"从设备读"。参数不对就打印用法提示，方便你知道怎么用。

2. **`./hello_drv_test -w "hello world"` → 无输出**
   程序打开 `/dev/hello`，调用 `write()` 把 `"hello world"` 送进内核，驱动里的 `hello_drv_write` 用 `copy_from_user` 把它拷贝进内核缓冲区。**没有报错 = 写入成功**（这个课程程序写成功后不打印任何东西，是正常的）。

3. **`ls /dev/hello` → 显示 `/dev/hello`**
   确认设备节点存在。`/dev/hello` 是**用户态访问驱动的"门牌"**，它内部记录着主设备号 240 / 次设备号 0。这个节点一般由 `mknod /dev/hello c 240 0` 手动创建，或由 udev/mdev 热插拔自动创建。

4. **`cat /proc/devices` → `Character devices: ... 240 hello ...`**
   `/proc/devices` 是内核的**虚拟文件**，列出当前内核里所有**已注册的设备驱动**，格式为「主设备号 + 驱动名」。重点看这一行：
   - **`240 hello`**：就是我们加载的驱动！`hello_drv_init` 里的 `register_chrdev(240, "hello", &hello_drv)` 把它注册成了主设备号 240 的字符设备驱动；
   - 列表里其他行（`mem`、`tty`、`fb`、`mtd`…）是内核自带的驱动，`adxl345`、`dht11`、`ds18b20` 等是 100ask 系统里其他演示驱动占用的号；
   - 下面 `Block devices:` 是块设备驱动（磁盘、MMC 卡等），和我们的字符设备无关。

**主设备号（240）有什么用？** 它是内核把"设备文件"和"驱动程序"对应起来的钥匙：当应用执行 `open("/dev/hello")` 时，内核从设备节点读出主设备号 240，就知道该调用 **`hello` 驱动**的 open 函数，而不是其他驱动。

**整条链路串起来**：

```
insmod hello_drv.ko
   └─> hello_init() → register_chrdev(240, "hello", ...)  驱动注册成功
        └─> /dev/hello 设备节点出现（主设备号 240）
             └─> hello_drv_test -w "hello world"
                  └─> open(/dev/hello) → 内核按主设备号 240 找到 hello 驱动
                       └─> write() → hello_drv_write() 把数据拷进内核缓冲区
```

这一节看到的三条证据互相印证，说明驱动已经**加载成功并且可用**：① `ls /dev/hello` 节点存在；② `/proc/devices` 里出现 `240 hello`；③ `-w` 写入没有报错。
