### 2.1.1 IO 系统
有两套 IO，一套是标准 IO，一套是系统调用 IO
![[Pasted image 20260826104937.png]]
- **APP** 可以直接调用 `open/read/write` 触发系统调用（走右侧直达内核的路径）。
- **APP** 也可以调用 `fopen/fread`，这部分在 C 库内部先经过用户空间的 buffer 处理，然后再调用底层的 `open/read/write` 进入内核（走左侧路径）。
所以，你的判断是对的：
- **`open/read/write`** 是用户态的**系统调用 API**。
- **`sys_open/sys_read/sys_write`** 是内核态对应的**具体实现函数**。

**POSIX** 是 **Portable Operating System Interface**（可移植操作系统接口）的缩写, `open/read/write` 也可以说是标准的 POSIX 调用。

### 2.1.3 使用 open 函数创建文件
使用这个 Open 函数创建文件的时候，你要给它的创建行为加上 O_CREAT 和 O_TRUNC，表示这个创建和这个截断。
同时，我们要给它后面的 mode 里面添加相应的权限。如果权限全给的话，就是 0777。0777 表示给读，给这个你自己，还要给组内的所有人**读写执行**的所有权限。
不过实际上，这个给 Group 里面其他人的权限，好像是不能给写权限的。
在 Linux 中，`0777` 是由三个**八进制数字**组成的，它们分别对应三种不同身份的人。
这三位数字从**左到右**，分别代表：
- **第 1 个数字（7）：所有者（User / Owner）**
    - **给谁？**：创建这个文件的**你自己**（或者是文件的主人）。
- **第 2 个数字（7）：所属组（Group）**
    - **给谁？**：这个文件所属的**用户组**。通常是和你同属于一个项目组、同一个部门的一群同事。
- **第 3 个数字（7）：其他人（Others）**
    - **给谁？**：既不是你自己，也不在你这个组里的**所有陌生人**（也就是系统里的其他所有普通用户）。

### 2.1.4 使用 dup 函数
dup 函数的作用是从一个文件描述符复制出一个新的文件描述符。新文件描述符的编号会接着增长，但会继承原文件描述符的读取位置或写入位置。
`dup2(fd1, fd2)` 会让 **fd 2** 指向 **fd 1** 所指向的同一个文件，fd 2 原先指向的文件会被关闭。所以，如果这个 fd 2 本身是标准输入、标准输出或者标准错误的话，就会出现一些有意思的状况，就可以实现类似输出到日志文件里面的效果。

### 2.1.5 Framebuffer 应用编程
首先，对于每个像素点，我们需要计算其偏移地址。偏移地址的计算方式为：Y 坐标乘以 X 轴分辨率，再加上 X 坐标，从而得到该像素点在整个图像中的偏移像素数。然后它偏移的像素数量乘上 bpp 除以 8 就是他的偏移量了。

颜色方面，相似的颜色表示我们一般分为三种方案：

1. RGB 888：对于红、绿、蓝分别分出 8 位，也就是一个字节来表示它们的颜色。每个字节就是每个字节能表示 0~255 的这个颜色范围吗？这个是很经典的 RGB 方案。
2. 第二种是 RGB 565，红色用 5 个 bit 来表示，绿色用 6 个 bit 表示，蓝色用 5 个 bit 表示。
3. 还有第三种是 RGB 555，就是红绿蓝三种颜色分别用 5 个 bit 来表示。

### 2.1.9 TCP 编程

#### 2.1.9.1 server
一般 TCP 编程分为四步：
1. 创建 Socket
2. 绑定（Bind）：将文件描述符与地址绑定在一起
3. 监听：让文件描述符开始监听，最简便的方式是监听 SO_MAXCONN
4. 接收：通过 accept 函数接收客户端的文件描述符。

韦老师讲的是接收到之后的进一步处理方式。在进一步处理方式中，我们开了一个子进程 fork，在子进程里开一个 while 1 循环，在 while 1 循环里面进行读取。

#### 2.1.9.2 client
客户端部分，我们是用与服务器相同的 IP 通过 connect 函数连接到服务器 socket，连接成功后创建一个 while (1) 循环检测用户输入。如果用户有输入，通过 fgets 获取用户输入，再通过 send 函数发送到服务器。

用法： `signal(信号, 处理方式)`
**每个信号有自己编码好的触发时机**

在这段代码中，`signal(SIGCHLD, SIG_IGN);` 的作用是**避免产生僵尸进程（zombie process）**。

1. **父子进程关系**：
    
    - 主进程（父进程）在 `accept` 到新连接后，调用 `fork()` 创建子进程。
        
    - 子进程负责与客户端通信（`recv` 循环），父进程继续等待新的连接。
        
2. **僵尸进程的产生**：
    
    - 当子进程终止时（例如客户端断开连接，子进程执行 `return -1;` 或 `exit`），内核会保留子进程的退出状态信息，直到父进程调用 `wait()` 或 `waitpid()` 来回收。
        
    - 如果父进程没有回收子进程，这些终止的子进程就会变成僵尸进程（`defunct`），占用系统进程表资源。
        
3. **`signal(SIGCHLD, SIG_IGN)` 的作用**：
    
    - `SIGCHLD` 信号在子进程终止、暂停或继续时发送给父进程。
        
    - 设置 `SIG_IGN`（忽略）后，内核会在子进程终止时自动回收其资源，**不会产生僵尸进程**，父进程也不需要显式调用 `wait()`。

#### 2.2.6.9 为什么生成 .ko？为什么 insmod 就能安装驱动？

**为什么不是把驱动编进内核，而是单独生成 .ko？**

- 内核镜像 `zImage` 是**静态**的：内容在编译时就固定了。如果所有驱动都编进去，改一个驱动就要重新编译整个内核并重启，开发和调试太慢。
- Linux 的解决方案是**可加载内核模块**（Loadable Kernel Module）：把驱动独立编译成一个 `.ko`（kernel object）文件，运行时**按需加载**进内核，不用重编内核、不用重启。
- `.o` 和 `.ko` 的区别：
  - `.o` 只是单个源文件的**编译产物**（目标文件），里面调用 `printk`、`register_chrdev` 等内核函数的符号还没解析，地址也没确定，不能直接运行；
  - `.ko` 是在 `.o` 基础上再经过**链接**（`ld -r`，把模块内多个目标文件合成一个）和**可重定位处理**，并附带了模块元数据（`.modinfo` 段：版本号 `vermagic`、许可证、描述、依赖等）。内核拿到它时，才知道怎么把代码装进内存、怎么补全它引用的地址。

**为什么 `insmod hello_drv.ko` 就能把驱动"安装"好？**

`insmod` 不是把文件复制到某个目录，而是把模块**加载进正在运行的内核**，由内核模块加载器完成 4 件事：

1. **加载进内核内存**：通过系统调用 `init_module()` 把 `.ko` 的代码/数据放进内核地址空间（用户程序运行在用户空间，驱动必须运行在内核空间）；
2. **符号解析 + 重定位**：把模块里引用的 `printk`、`register_chrdev` 等**内核导出符号**的地址填上去，让驱动能调用内核函数；
3. **校验版本**：检查模块的 `vermagic`（编译时写死的内核版本 + 配置）是否与当前内核匹配，不匹配会直接拒绝加载——这就是为什么驱动必须用 2.1.6.1 编好的**同一个内核**来编译；
4. **调用入口函数**：执行 `module_init(hello_drv_init)`，也就是 `hello_drv.c` 里的 `hello_drv_init`，它在这里完成真正的注册（比如 `register_chrdev` 注册字符设备、创建设备节点）。到这步驱动才"生效"，应用才能访问它。

对应的卸载：`rmmod hello_drv` 会调用 `module_exit` 的退出函数并释放资源。

> ⚠️ 注意：`insmod` 只是把驱动加载进"**正在运行的内核内存**"，**重启后消失**。想开机自动加载，才需要把 `.ko` 放到开发板文件系统的 `/lib/modules/$(uname -r)/` 下，再 `depmod` + `modprobe hello_drv`。

#### 2.2.6.10 上机测试：`hello_drv_test` 的输出解读

这是 `insmod hello_drv.ko` 之后，运行测试程序 `hello_drv_test` 的终端记录：

```bash
[root@100ask:~]# ./hello_drv_test
Usage: ./hello_drv_test -w <string>
       ./hello_drv_test -r

[root@100ask:~]# ./hello_drv_test -w "hello world"
[root@100ask:~]# ls /dev/hello
/dev/hello

[root@100ask:~]# car /proc/devices
-bash: car: command not found
[root@100ask:~]# cat /proc/devices
Character devices:
  1 mem
  ...
226 drm
240 hello
241 adxl345
  ...
254 gpiochip

Block devices:
  1 ramdisk
  ...
179 mmc
[root@100ask:~]#
```

逐条解释：

1. **`./hello_drv_test`（不带参数）→ 打印 Usage**
   测试程序的 `main()` 会检查参数：`-w <string>` 表示"往设备写一段字符串"，`-r` 表示"从设备读"。参数不对就打印用法提示，方便你知道怎么用。

2. **`./hello_drv_test -w "hello world"` → 无输出**
   程序打开 `/dev/hello`，调用 `write()` 把 `"hello world"` 送进内核，驱动里的 `hello_drv_write` 用 `copy_from_user` 把它拷贝进内核缓冲区。**没有报错 = 写入成功**（这个课程程序写成功后不打印任何东西，是正常的）。

3. **`ls /dev/hello` → 显示 `/dev/hello`**
   确认设备节点存在。`/dev/hello` 是**用户态访问驱动的"门牌"**，它内部记录着主设备号 240 / 次设备号 0。这个节点一般由 `mknod /dev/hello c 240 0` 手动创建，或由 udev/mdev 热插拔自动创建。

4. **`cat /proc/devices` → `Character devices: ... 240 hello ...`**
   `/proc/devices` 是内核的**虚拟文件**，列出当前内核里所有**已注册的设备驱动**，格式为「主设备号 + 驱动名」。重点看这一行：
   - **`240 hello`**：就是我们加载的驱动！`hello_drv_init` 里的 `register_chrdev(240, "hello", &hello_drv)` 把它注册成了主设备号 240 的字符设备驱动；
   - 列表里其他行（`mem`、`tty`、`fb`、`mtd` …）是内核自带的驱动，`adxl345`、`dht11`、`ds18b20` 等是 100 ask 系统里其他演示驱动占用的号；
   - 下面 `Block devices:` 是块设备驱动（磁盘、MMC 卡等），和我们的字符设备无关。

**主设备号（240）有什么用？** 它是内核把"设备文件"和"驱动程序"对应起来的钥匙：当应用执行 `open("/dev/hello")` 时，内核从设备节点读出主设备号 240，就知道该调用 **`hello` 驱动**的 open 函数，而不是其他驱动。

**整条链路串起来**：

```
insmod hello_drv.ko
   └─> hello_init() → register_chrdev(240, "hello", ...)  驱动注册成功
        └─> /dev/hello 设备节点出现（主设备号 240）
             └─> hello_drv_test -w "hello world"
                  └─> open(/dev/hello) → 内核按主设备号 240 找到 hello 驱动
                       └─> write() → hello_drv_write() 把数据拷进内核缓冲区
```

这一节看到的三条证据互相印证，说明驱动已经**加载成功并且可用**：① `ls /dev/hello` 节点存在；② `/proc/devices` 里出现 `240 hello`；③ `-w` 写入没有报错。

![[Pasted image 20260910110829.png]]
- **`00` (Clock is off during all modes)**：
    - **含义**：在所有模式下，时钟都关闭。
    - **结果**：这就是彻底的**关闭时钟**。如果你往 GPIO 2 的 CG 位写入 `00`，GPIO 2 模块就会因为没有时钟而停止工作（无法读取引脚状态，也无法输出）。
    - _注：括号里还提到“Stop enter hardware handshake is disabled”，这是针对停止模式的一个硬件握手信号被禁用了，我们平时做普通驱动开发可以暂时忽略这半句。_
        
- **`01` (Clock is on in run mode, but off in WAIT and STOP modes)**：
    - **含义**：在正常运行模式（Run mode）下时钟开启，但在等待（WAIT）和停止（STOP）这种低功耗模式下时钟关闭。
    - **结果**：这是**最常用的配置**。系统正常跑的时候，GPIO 正常工作；当系统进入休眠（STOP/WAIT）时，为了省电，这个 GPIO 的时钟自动关掉。
    - **注意**：如果你的设备从 STOP 模式唤醒后需要立刻操作 GPIO，硬件会自动重新开启这个时钟，不需要软件干预。
	
- **`10` (Not applicable Reserved)**：
    - **含义**：保留值，不适用。
    - **结果**：**千万不要写 `10`**。这是未定义的，可能会导致芯片产生不可预期的行为（比如死机或总线错误）。
        
- **`11` (Clock is on during all modes, except STOP mode)**：
    - **含义**：在所有模式下时钟都开启（除了 STOP 模式）。
    - **结果**：这是**一直保持开启**的配置。无论系统怎么休眠（除非进入最深的 STOP 模式），这个时钟都一直开着。
    - **应用场景**：通常用于那些在低功耗模式下（如 WAIT 模式）仍然需要工作，以便能把系统唤醒的外设（比如某些唤醒源引脚）。不过图中的注释说 except STOP mode，意味着如果进了 STOP，它也会关。具体要看芯片手册对 STOP 模式的定义。

你的理解基本正确，但需要补充一个关键点：**设备号是否由内核自动分配，完全取决于你传入的 `major` 参数**。

根据 Linux 内核文档，`register_chrdev` 的行为分两种情况[](https://android.googlesource.com/kernel/common/+/d247e2c661f28a21e5f9a8d672e1e88a7c1c5d4a%5E%21/fs/char_dev.c)[](https://manpages.debian.org/experimental/linux-manual-4.11/__register_chrdev.9)：

**情况一：传入 `major = 0` ——内核动态分配**  
此时内核会寻找一个空闲的主设备号分配给你的驱动，并将这个**分配好的主设备号作为返回值**返回。所以写法通常是：
``` c
major = register_chrdev(0, "my_device", &fops);
```
返回值就是内核分配的主设备号，你用变量 `major` 接收它，后续 `unregister_chrdev(major, ...)` 时要用这个值[](https://developer.aliyun.com/article/1269153#1)[](https://wiki.i2som.com/docs/embeddeddevwiki/embeddeddevwiki-1gfl598vbn41m)。

**情况二：传入 `major > 0` ——静态指定**  
你指定一个具体的主设备号，内核尝试注册这个号。如果成功，**返回值为 0**（注意不是返回主设备号本身）；如果该号已被占用，返回 `-EBUSY` [](https://developer.aliyun.com/article/1269153#1)[](https://sources.debian.org/src/manpages-fr/0.8-1/man9/register_chrdev.9/#1)。

- [00:02:50](https://www.bilibili.com/video/BV1w4411B7a4/?t=170.402088#t=02:50.40) 给内核提供入口函数和出口函数，相当于这个设备的析构和构造函数（？）

你的理解方向是对的，但用“构造函数/析构函数”来类比需要稍微修正一下——**入口函数和出口函数不是“构造/析构一个对象”，而是“注册/注销一个驱动”**。

| C++ 概念 | 驱动中的对应             | 区别                                 |
| ------ | ------------------ | ---------------------------------- |
| 构造函数   | 入口函数 `module_init` | 构造函数是创建对象时自动调用；入口函数是**加载模块时**由内核调用 |
| 析构函数   | 出口函数 `module_exit` | 析构函数是对象销毁时自动调用；出口函数是**卸载模块时**由内核调用 |
关键区别在于：**构造函数/析构函数操作的是“对象实例”，而入口/出口函数操作的是“驱动模块本身”**。入口函数里做的事情通常是：

- 注册设备号（`register_chrdev`）
- 注册 `file_operations`
- 创建 `class` / `device` 节点
- 初始化硬件

出口函数则相反：注销设备号、销毁设备节点、释放资源。

如果你把“设备”理解为一个对象，那更贴近“构造/析构”的其实是：

- **`open` 函数**：类似“构造”——每次应用程序打开设备时调用，可以在这里初始化硬件、申请资源
    
- **`release` 函数**：类似“析构”——每次应用程序关闭设备时调用，释放 `open` 里申请的资源
    

而 `module_init` / `module_exit` 更像是**整个驱动模块的生命周期管理**，只在你 `insmod` / `rmmod` 时各执行一次。

- 原因在于同时运行两个 APP 时，会分配不同的进程，也就分配不同的物理地址。但是对于同一个程序里的变量，它们的虚拟地址是一样的，且不会互相影响。这是因为我们对不同的物理地址都进行了 IO Remap 映射，所以虚拟地址的一个作用就是把不同的物理地址隔离开来。
- MMU（内存管理单元） 两大作用：
1. 地址映射：CPU 发出同样的地址 (虚拟地址)，执行不同的 APP 由 MMU 执行这个转换
2. 权限保护：CPU 发出的地址，要经过 MMU 审核之后才可以访问
> MMU = **翻译官**（虚拟地址翻译成物理地址）+ **保安**（检查这次访问有没有权限）。

**Driver 不是“通用的驱动框架”，而是“针对某一类设备的驱动逻辑”；Device 是“具体硬件的信息”。**

更准确地说：

- **Device**：描述“这里有一个什么硬件”。比如地址、中断号、时钟、寄存器基址、设备名字/兼容性字符串等。它回答的是“**在哪、是什么**”。
    
- **Driver**：描述“怎么操作这一类硬件”。比如 probe 函数、读写寄存器、中断处理、电源管理等。它回答的是“**怎么用**”。
    
- **Bus（总线）**：负责把两者匹配起来。你笔记里说的“两个链表一一比较”就是总线在做匹配。匹配成功后调用 driver 的 probe，并把 device 的信息传进去。
    

所以为什么要分开？核心原因是**解耦**：

1. **同一驱动可支持多个设备**  
    比如一个 `gpio-keys` 驱动，可以匹配很多块板子上的按键设备，只是 Device 描述不同。
    
2. **同一设备可换驱动**  
    同一块硬件，在 Linux 下可以用不同驱动去操作（比如厂商驱动 vs 通用驱动），Device 不变，Driver 可换。
    
3. **设备信息经常变，驱动逻辑相对稳定**  
    板子改了、地址变了、中断号变了，只改 Device（现在多用设备树 dts），驱动代码不用动。
    
4. **支持热插拔和动态匹配**  
    设备插入后注册 Device，总线自动找匹配的 Driver；驱动加载后注册 Driver，总线自动找已存在的 Device。
    

你提到的“不同厂商的设备”这个说法要小心：  
不是“一个厂商一个 Device 结构体”，而是**每个具体的硬件实例对应一个 Device**。厂商差异通常体现在 Device 的 compatible 属性、资源信息里，Driver 通过匹配这些信息来决定是否支持。

用一句话总结就是：

> **Device 是“硬件身份证”，Driver 是“操作说明书”，Bus 是“婚介所”，负责把身份证和说明书配对。**

你笔记里说的“通过 driver_override 或 name/id_table 匹配”，正是这个配对过程的两种方式。

#### 2.2.14.1 怎么写程序

①分配/设置/注册 platform_device 结构体
在里面定义所用资源，指定设备名字。

②分配/设置/注册 platform_driver 结构体

**`register_led_operations` 不是注册设备**，它只是把你自己的函数指针存进 `p_led_opr` 这个全局变量，供 `led_drv_write` 调用。它跟 platform 总线**没有任何关系**。
所以：
- 设备：`board_A_led.c` 里注册
- 驱动：`chip_demo_gpio.c` 里 `platform_driver_register` 
- 操作函数组：`chip_demo_gpio.c` 里 `register_led_operations`

#### 2.2.15.1 为什么会有“我只注册了设备”的错觉？
因为 `platform_device` 那部分可能被**设备树**替代了。如果板子用设备树，那 `board_A_led.c` 里就没有 `platform_device_register`，设备是内核**解析 .dts 时自动注册**的。

这时你看到的代码里：
- 设备：**看不见**（在 .dts 里）
- 驱动：`platform_driver_register`
- 操作函数组：`register_led_operations`

所以不是“只注册了设备”，而是**三样东西分散在三个地方，你只注意到了后两行**。

#### 2.2.15.2 `probe` 是不是类似构造函数？
**非常像，可以这么理解，但有几处关键区别。**

| 构造函数          | `probe`                |
| ------------- | ---------------------- |
| 对象被创建时自动调用    | 驱动和设备配对成功时自动调用         |
| 做初始化：分配资源、设初值 | 做初始化：拿资源、注册操作函数、创建设备节点 |
| 你不需要手动调用它     | 你不需要手动调用它，内核调          |

### 2.2.18 内核对设备树的处理与使用
#### 2.2.18.1 哪些节点会被转换成 platform_device？
1. 根节点下含有 compatile 属性的子节点
2. 含有特定 compatile 属性的节点的子节点
   如果一个节点的 compatile 属性，它的值是这 4 者之一: "simple-bus","simple-mfd","isa","arm, amba-bus",
   那么它的子结点 (需含 compatile 属性) 也可以转换为 platform_device。
3. 总线 I 2 C、SPI 节点下的子节点：不转换为 platform_device
   某个总线下到子节点，应该交给对应的总线驱动程序来处理，它们不应该被转换为 platform_device.

#### 2.2.18.2 一句话总结匹配

`compatible` = **设备和驱动之间的“匹配暗号”**，两边各列一个支持列表，求交集，非空就配对成功、调 `probe`。

---

#### 2.2.18.3 核心要点

| 问题                  | 结论                                     |
| ------------------- | -------------------------------------- |
| `compatible` 是什么    | 设备/驱动的**匹配键**，也是**支持列表**               |
| 两边都可以多个吗            | 可以，设备侧是字符串列表，驱动侧是 `of_device_id` 数组    |
| 多个怎么匹配              | **双重循环，任意一对相等即成功**，复杂度 O (n×m)          |
| 规模大吗                | n、m 通常 1~3，且只在注册时匹配一次，**开销可忽略**        |
| 没有 `compatible` 会怎样 | 不转 `platform_device`，或匹配失败，**不 probe** |
|哪些节点故意不写| `chosen`、`memory`、`simple-bus` 容器等，**本来就不需要驱动**|
