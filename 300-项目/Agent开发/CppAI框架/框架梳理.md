## 2.1 day 11

聊天上下文的隔离
开始对于整个服务器，只有一个全局的 AI Helper
这显然是不合理的，所以我们需要对每个用户进行拆分，划分一个字典，让每个用户都有一个 AI helper。我们会发现，即使对于一个用户，分一个 AI helper 也是不够的，因为每个用户可能开多个会话。对于每一个会话的上下文，我们都应该将其隔离开来，所以应该提供一个两层的字典。

ai helper 中的数据格式是用一个存储 pair 的 vector 实现的。pair 里面前面是文字，后面是时间戳。它是奇偶分组的：偶数下标存储的是用户的提问，奇数下标存储的是 AI 的回答。
Chat information 是所有对话的一个集合，存储多个User sessions，通过 user id 作为索引；下面的 user sessions 是 chat information 底下的元素, 是一个存储 AI helper 的字典，通过 session id 作为索引；ai helper 则是 user session 底下的元素。

ChatCreateAndSendHandler：首次聊天的时候会调用 
ChatSendHandler：在并非首次聊天的时候，会加入 Session ID
ChatHistoryHandler：切换其他会话的时候，需要展示其他会话的聊天历史
冷启动恢复：readDataFromMySQL，重新登录时，由于当前没有缓存，需要从 SQL 中重新读取之前的会话数据。

### 2.1.1 AIHelper::chat() 内部做了什么

这是整个链路中最核心的执行体。当一个 Handler 拿到 `AIHelperPtr` 并调用 `chat()`，内部发生：

```
chat(userId, username, sessionId, userQuestion, modelType)
│
├─ 1. 选择模型策略 (StrategyFactory, 根据 modelType)
│      "1" = 阿里百炼  "2" = 豆包  "3" = 百炼RAG  "4" = MCP
│
├─ 2. addMessage(user, true, userQuestion, sessionId)
│       → messages.push_back({userQuestion, timestamp})
│       → pushMessageToMysql(...) → RabbitMQ(sql_queue) → 异步入库
│
├─ 3. strategy->buildRequest(this->messages)
│       把整个 messages 历史构造成大模型的 chat completion 请求体
│       system prompt + 历史对话 + 当前问题
│
├─ 4. executeCurl(payload)
│       HTTP POST 调用大模型 API, 等待返回
│
├─ 5. strategy->parseResponse(response)
│       从 JSON 响应中提取 AI 的文本回答
│
├─ 6. addMessage(user, false, answer, sessionId)
│       → messages.push_back({answer, timestamp})
│       → pushMessageToMysql(...) → RabbitMQ → 异步入库
│
└─ 7. return answer
```

关键点：每次调用 chat() 会在 messages 里追加**两条**消息（用户一条，AI一条），维持了"偶数下标是用户、奇数下标是 AI"的约定。
