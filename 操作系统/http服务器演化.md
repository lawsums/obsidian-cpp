## 标准答案
### 1、为什么早期HTTP是短连接，请求一次就断开
本质就是**服务器资源有限**，早期线程很重，如果一直保持TCP长连接，会长期占用线程，服务器很快被占满、扛不住并发，所以干脆请求完立刻断开，释放线程资源。

### 2、HTTP1.1 为什么改成长连接
为了**用户体验+网络性能**，不用每次请求都重复三次握手、四次挥手，复用一条TCP连接传多次请求，减少开销、加快网页加载；
但**依旧是半双工**，只能客户端主动请求，服务端不能主动推送数据。

### 3、为什么需要 WebSocket
业务有**实时双向通信需求**（聊天、通知、弹幕），HTTP做不到服务端主动推消息；
WebSocket基于TCP、HTTP握手后升级协议，**真正全双工**，服务端可随时主动发消息，完全为**实时用户体验**而生，是永久长连接。

### 4、WebSocket 项目为什么要用协程
WebSocket 每条都是**常驻长连接**，在线用户一多，如果一个连接开一个线程：
线程内存大、数量有上限、上下文切换开销高，服务器直接扛不住。
协程**极轻量、占用资源少、阻塞不卡死线程**，能用少量线程承载几十万WebSocket长连接，**纯粹为了高并发性能、扛大量用户**。

### 整条演进逻辑一句话背下来
一开始HTTP短连接是**怕占线程、省服务器资源**；
HTTP1.1长连接是**优化体验、减少握手开销**；
WebSocket是**为了实现实时双向通信、提升用户体验**；
最后上协程是**用户太多，用轻量模型解决WebSocket高并发性能压力**。

### 一、TCP 可靠稳定，但为什么没有数据边界？
1. TCP 是**面向字节流**，像一根水管，只负责把字节**按顺序、不丢、不乱**送达，**不帮你区分哪一段是一条业务消息**。
2. 底层有**Nagle算法、MTU分片、内核缓冲区**，会把多次发送的数据自动合并、拆分，所以产生**粘包**，没有天然边界。
3. 总结：**TCP只保证字节可靠传输，不负责划分消息边界**，边界要应用层自己处理。

### 二、UDP 有数据边界，为什么实时性更好？
1. UDP 是**面向报文**，一次发一个报文、收只能收一个，自带**天然数据边界**，不会粘包。
2. UDP **无连接、无确认应答、无超时重传、无拥塞控制**，少了很多校验和等待逻辑，**延迟极低**。
3. 缺点：不保证可靠、可能丢包乱序；适合**直播、语音、游戏**，宁愿丢一点数据也不能卡顿延迟。
4. 总结：**UDP省去了TCP的可靠校验开销，所以实时性强；自带报文边界，不会粘包**。

### 三、HTTP1.1 长连接、长轮询、WebSocket 区别（背诵版）
#### 1. HTTP1.1 长连接
- 本质：**半双工，一问一答**
- 特点：TCP 不断开复用连接，**只能客户端主动发请求，服务端不能主动推消息**
- 问题：想实时只能客户端定时轮询，浪费请求、延迟高
- 用途：普通网页、接口请求

#### 2. 长轮询 Long Polling
- 本质：**基于HTTP的伪实时**
- 流程：客户端发请求 → 服务端挂起不响应 → 有数据再返回 → 客户端立刻再发起下一次请求
- 特点：还是HTTP、半双工，**兼容所有环境**，实时性中等，比定时轮询好很多
- 用途：后台消息、简单通知、老旧项目兼容

#### 3. WebSocket
- 本质：**TCP基础上的独立协议，HTTP握手升级**
- 特点：**真正全双工双向通信**，客户端、服务端随时可以互相发消息；永久长连接，头部开销小、延迟低
- 配套：连接太多用**协程**降低开销，支撑海量长连接
- 用途：聊天室、弹幕、实时对战、协同编辑

### 四、把整套逻辑串成一段万能口述（面试直接背）
TCP 是面向字节流，只保证可靠有序传输，不划分消息边界，所以会粘包；UDP 是面向报文，自带数据边界，而且没有 TCP 复杂的确认、重传和拥塞机制，开销小、实时性更好。
HTTP1.1 长连接只是复用 TCP 连接，依旧是一问一答半双工，服务端无法主动推送；长轮询利用 HTTP 挂起请求实现伪实时，兼容好但不是真正双向；WebSocket 通过 HTTP 握手升级为独立协议，实现全双工双向实时通信，适合高实时场景，又因为是海量长连接，所以配合协程来提升并发承载性能。
